# Технічне завдання: OpenCode Android Linux Workspace

- **Статус:** продуктова специфікація / ТЗ для MVP та наступних етапів
- **Платформа:** Android, перша цільова архітектура `arm64-v8a`
- **Робоча назва:** OpenCode Android
- **Рантайм:** Debian або Ubuntu rootfs у приватному сховищі застосунку, запуск через `fake-chroot-ng`
- **Референс UX/архітектури:** Hermes Loader (`com.hermes.loader`)

## 1. Мета продукту

Надати користувачу Android зручне Linux-середовище для OpenCode: встановлення системи однією дією, запуск агента, доступ до локального вебінтерфейсу та оболонки Linux. Звичайному користувачу не потрібно знати про rootfs, OCI-шари, apt або параметри контейнера. Досвідчений користувач має мати контроль над додатковими пакетами й кількома незалежними консолями.

Застосунок не є повною віртуальною машиною і не надає Android root. `fake-chroot-ng` забезпечує userspace-сумісність/перенаправлення шляхів, але не є межею безпеки для запуску ворожого коду. Rootfs і процеси належать UID застосунку.

## 2. Цільові користувачі та режими

### 2.1 Простий режим

Для користувача, який хоче швидко почати працювати з OpenCode.

- Вибір одного з двох образів: **Debian Slim** або **Ubuntu Minimal**.
- Вибрана система чітко позначена; рекомендований варіант може мати бейдж «Рекомендовано».
- Картка OpenCode показана нижче вибору ОС і встановлюється в обране середовище.
- Велика основна кнопка **«Встановити»** запускає повний сценарій: rootfs → базова конфігурація → спільні залежності → OpenCode.
- Прогрес відображає поточний крок, загальний стан, швидкість/обсяг завантаження там, де доступно, і повідомлення про помилку.
- Журнал прихований у згорнутій панелі **«Деталі встановлення»**, його можна розгорнути, виділити й скопіювати.
- Після завершення показати дії **«Відкрити OpenCode»**, **«Відкрити Web»** і **«Shell»**.
- Авторизація/ключі провайдера налаштовуються самим користувачем у підтримуваному інтерфейсі OpenCode; застосунок не збирає й не пересилає секрети.

### 2.2 Розширений режим

Для користувачів, які самі керують Linux-середовищем.

- Ті самі Debian/Ubuntu rootfs та спільне ядро інсталятора.
- Вибір профілю пакетів і окремих пакетів із категоріями та коротким описом.
- Запуск довільних команд у Shell, включно з `apt install`.
- Кілька вкладок/сесій консолі одночасно; кожна має власний PTY, процес, робочу директорію, назву й журнал.
- Дії для сесії: створити, перейменувати, перемкнутися, завершити; завершення однієї сесії не повинно завершувати інші.
- Набори налаштувань оболонки (наприклад bash/zsh), імпорт/експорт текстових конфігів лише після явного підтвердження.
- Додаткові інструменти, наприклад `zsh`, `git`, `curl`, `python3`, `build-essential`, `tmux`, `vim`/`nano`, `mc`/`ranger`/`lf` (конкретний набір потребує перевірки доступності та сумісності в обох дистрибутивах).
- Небезпечні або великі компоненти мають показувати пояснення, розмір і запитувати підтвердження.

Перемикання режиму не видаляє rootfs, конфігурацію чи файли користувача.

## 3. Стартовий екран і візуальна мова

### 3.1 Принципи

- Візуальна мова: мінімалістична, натхненна macOS, але з Android-native поведінкою.
- Чітка ієрархія, великі відступи, спокійні поверхні/картки, округлені кути, акцентний колір для основної дії.
- Світла й темна теми, доступні розміри шрифту, достатній контраст і великі touch-targets.
- Уникаємо реклами в консолі, під час встановлення й на екрані помилок.

### 3.2 Структура стартового екрана

1. Верхня панель: логотип/назва, індикатор стану системи, перемикач **Простий / Розширений**, кнопка налаштувань.
2. Заголовок на кшталт «Твоя Linux-середа для OpenCode» і коротке пояснення.
3. Секція **Операційна система** з двома картками:
   - Debian Slim — компактна Debian-система; рекомендована для першого запуску.
   - Ubuntu Minimal — мінімальне Ubuntu-середовище.
   - Показувати архітектуру, джерело образу та оцінку завантаження/дискового простору, якщо їх можна достовірно визначити.
4. Секція **Інструменти**: OpenCode (обов’язковий для кнопки швидкого встановлення), у розширеному режимі — додаткові компоненти.
5. Основна велика кнопка **«Встановити»** (або **«Встановити/відновити»** відповідно до стану).
6. Під час інсталяції — індикатор етапів, прогрес завантаження/розпакування, кнопка розгортання журналу; закриття екрана не повинно тихо зупиняти критичну операцію без попередження.
7. Після готовності — картки швидкого запуску OpenCode, Web та Shell.

### 3.3 Стани

`Not installed` → `Downloading rootfs` → `Verifying` → `Extracting` → `Preparing Debian/Ubuntu` → `Installing tools` → `Installing OpenCode` → `Ready`.

Додаткові стани: `Paused/Cancelled`, `No space`, `Network error`, `Checksum mismatch`, `Unsupported ABI`, `Runtime probe failed`, `Rootfs corrupted`, `OpenCode setup required`, `Server starting`, `Server ready`, `Process exited`.

Кожна помилка має людське пояснення, конкретний крок відновлення й доступ до повного копійованого журналу.

## 4. Встановлення системи

### 4.1 Єдиний спільний конвеєр

Вибір Debian/Ubuntu задає тільки опис джерела образу, версію/дистрибутив і метадані. Спільні частини: перевірка архітектури та runtime, завантаження, верифікація, розпакування, підготовка DNS/`/proc`/`/dev` за можливостями runtime, каталогів persistence, встановлення пакетів, маркер версії, відкат після помилки.

**Не вважати образ завжди одним URL на tar-файл.** Офіційні образи можуть бути OCI manifest + кілька шарів. Для OCI потрібні вибір `linux/arm64`, перевірка digest кожного шару, правильне накладання шарів та обробка `.wh.*`/opaque whiteouts. Альтернатива — офіційний rootfs tarball із зафіксованим SHA-256 і чіткою ліцензією/джерелом. Не встановлювати образ без верифікації цілісності.

### 4.2 Безпечне розгортання

- Завантажувати у тимчасове staging-сховище з обмеженням розміру й видимим прогресом.
- Перевіряти SHA-256/OCI digest **до** застосування шару.
- Захищатися від path traversal (`..`, абсолютні шляхи), некоректних symlink/hardlink і надмірних файлів.
- Не створювати device nodes; ownership застосунку не змінювати.
- Перевірити наявність очікуваних файлів (`/bin/bash`, `/etc/os-release`, архітектуру).
- Активувати rootfs атомарною заміною `rootfs.new` → `rootfs`; невдала інсталяція не повинна псувати чинну систему.
- Версію й джерело записувати в marker із датою, архітектурою та digest.
- Показувати попередження про потрібне місце до завантаження, але остаточну оцінку рахувати з метаданих образу.

### 4.3 Вибір джерел

Підтримувати каталог конфігурацій образів, наприклад `DistroSpec(id, displayName, release, arch, source, digest/manifest policy, expected markers)`. Debian/Ubuntu кнопки мають бути конфігураціями, не різними форками інсталятора. Пінити релізи або перевіряти актуальний manifest; не покладатися на неперевірений `latest`.

## 5. Пакети та OpenCode

### 5.1 Базовий набір

Спільний мінімум узгодити так, щоб OpenCode працював в обох системах. Очікувані кандидати: `ca-certificates`, `curl`, `git`, `bash`, `nodejs`, `npm`, `python3`, `python3-venv`, `build-essential` (частину можна винести в профіль). Остаточний список треба перевірити на фактичних вимогах OpenCode і розмірі образу.

### 5.2 OpenCode

- Установлювати у guest через офіційно документований командний спосіб: `npm install -g @opencode/cli`.
- Перевіряти код завершення, версію (`opencode --version`) і доступність команди `opencode` в `PATH`.
- Не робити прихованої авторизації. Користувач сам запускає підтримуваний OpenCode sign-in/auth або налаштовує провайдера.
- Конфіги, токени й стан OpenCode мають зберігатися в окремому persistent HOME/config каталозі; заборонено виводити їх у журнали/аналітику.
- Якщо npm package/постінсталяційний скрипт не підтримує цільовий ARM64 Debian/Ubuntu, показати зрозуміле повідомлення й дозволити встановлення офіційного Linux ARM64 binary як альтернативу тільки після явного вибору/підтвердження.

### 5.3 Розширені профілі

Профілі описуються даними/маніфестом: назва, опис, apt-пакети, приблизний розмір за оцінкою apt, конфлікти, restart hints. Приклад профілю «Розробник»: `git`, `python3`, `python3-venv`, `npm`, `build-essential`, `tmux`, `zsh`. «Файлові менеджери»: один або кілька з підтримуваних пакетів. Усі пакети ставляться через `apt`, а не включаються в APK.

## 6. Shell та кілька вкладок

- Shell працює **в Debian/Ubuntu guest через fake-chroot-ng**, не в Android host shell.
- Повноцінний інтерактивний CLI вимагає PTY: коректна ширина/висота, resize, stdin, сигнали Ctrl-C/Ctrl-D, ANSI escape sequences, UTF-8 та клавіші-модифікатори.
- Простий pipe не називати інтерактивним терміналом і не використовувати як підміну.
- У розширеному режимі кожна вкладка — окремий PTY/process/session, що має ID, заголовок, cwd, час старту та стан.
- Перехід між вкладками не вбиває процес; lifecycle керується foreground service за вимогами Android, з коректним повідомленням системи, якщо сесія може бути завершена ОС.
- Вкладка OpenCode Web/CLI не повинна перехоплювати чужий ввід іншої сесії.
- Обмежити пам’ять журналу й підтримати копіювання виділеного тексту/всього журналу.

## 7. OpenCode Web і локальний сервер

- Вебрежим запускає офіційний підтримуваний OpenCode web/server command усередині обраного rootfs.
- За замовчуванням слухати лише `127.0.0.1`, не відкривати сервер на LAN/`0.0.0.0` без окремого попередження, автентифікації й явної згоди.
- Перевіряти готовність сервера health endpoint/HTTP відповіддю з тайм-аутом; лише після цього відкрити WebView або показати URL.
- Керування START/STOP, портом, логом, станом сервера; обробляти зайнятий порт та аварійний вихід.
- WebView за замовчуванням навігує тільки до loopback-origin; зовнішні URL відкривати системним браузером, не надавати довільним сайтам native bridge.
- Тримати процес у foreground service за потреби; при зупинці акуратно завершити сервер і дочірні процеси.
- Перевірити, чи підтримує OpenCode server потрібний вбудований web UI у вибраній версії; не вважати API endpoint сам собою повноцінним dashboard.

## 8. Persistence і каталоги

Розділяти **rebuildable** систему й **цінні дані користувача**:

- `files/rootfs/` або версійований `rootfs/<distro>/<release>/<arch>/` — видалюваний/перевстановлюваний userspace.
- `files/storage/home/` — Linux HOME.
- `files/storage/opencode/` — конфігурація/стан OpenCode (потрібні точні upstream paths і bind mounts).
- `files/storage/workspace/` — файли проєктів.
- `files/storage/logs/` — діагностичні журнали з обмеженим retention.
- `files/cache/` — неповні/завантажені архіви; безпечне очищення лише після завершення операцій.

Rootfs reinstall/update не повинен видаляти HOME, workspace, конфіги чи сесії. Перед destructive дією показати, що саме буде видалено, і вимагати підтвердження.

## 9. Налаштування та налаштування UI

- Проста/розширена схема вибору.
- Керування rootfs (версія, використаний простір, перевстановлення, перевірка цілісності).
- Перелік встановлених пакетів/профілів.
- OpenCode version/provider setup guidance; застосунок не зберігає секрети окремо від OpenCode.
- Налаштування теми, шрифту термінала, прокрутки, shell, робочої теки.
- Імпорт/експорт профілю інструментів як JSON без секретів.
- Інформація про ліцензії Debian/Ubuntu, OpenCode, `fake-chroot-ng` та сторонні бібліотеки.

## 10. Монетизація (не блокер MVP)

Можлива модель:

- **Free:** просте встановлення однієї Linux-системи + OpenCode, локальний Web/Shell, ненав’язлива реклама лише поза терміналом і критичними потоками.
- **Pro:** без реклами, розширений менеджер пакетів/профілів, багатовкладкові консолі, додаткові конфіги та зручності.

Не блокувати базову Shell/можливість користувача встановлювати пакети командою `apt` платною стіною. Pro має продавати готові профілі, UX, менеджер сесій, підтримку/резервні копії, а не самі відкриті пакети Debian. Рекламу/білінг відкласти до перевірки попиту й стабільності. Не додавати tracking вмісту terminal/rootfs.

## 11. Нефункціональні вимоги

- Підтримка `arm64-v8a` у першій версії; інші ABI не показувати як підтримані без тестів.
- Мінімальна Android версія згідно Gradle/manifest; rootless, без запиту root.
- Мережеві операції з таймаутом, retry/backoff, відновленням/чітким restart path.
- Інсталяція не блокує UI thread; progress повідомляється регулярно.
- Доступність: screen reader labels, контраст, масштабування шрифту, достатні touch targets.
- Не логувати токени, auth headers, private keys, повний вміст секретних конфігів.
- Усі процеси мають контрольований lifecycle і не залишати невидимих daemon-ів після STOP.

## 12. Перевірки якості та критерії приймання

### Rootfs
- Debian і Ubuntu manifest вибирають строго `linux/arm64`.
- Перевірка digest перед розпакуванням; негативний тест із пошкодженим layer завершується помилкою без активації.
- Тест path traversal, symlink, hardlink, whiteout/opaque whiteout для OCI.
- Переривання мережі/нестача диска не псують поточний rootfs і persistent storage.
- Після першого старту `/etc/os-release` має відповідати обраному дистрибутиву.

### Runtime/OpenCode
- `chroot-ng --probe` на підтримуваному пристрої.
- Усередині guest працюють `apt-get update`, `python3 --version`, `node --version`, `npm --version`, `git --version`, `curl --version`.
- `npm install -g @opencode/cli` завершується успішно; `opencode --version` повертає код 0.
- Користувацькі auth/config файли зберігаються після перевстановлення rootfs.

### Shell/Web
- PTY: ввід, Ctrl-C, resize, UTF-8, ANSI, вихід із shell.
- Декілька вкладок працюють незалежно, процес зберігається при перемиканні.
- Web readiness перевіряється до навігації; STOP завершує сервер.
- За замовчуванням порт доступний лише локально; спроба зовнішнього доступу не проходить.

### UX/CI
- Велика кнопка встановлення і дистрибутивні картки працюють у світлій/темній темі.
- Прогрес видно, журнал розгортається, копіювання працює.
- CI будує debug APK; unit-тести для manifest selection, digest і archive safety.
- До релізу — тест на реальному Android arm64, не лише емуляторі.

## 14. Ризики й відкриті технічні питання

- `fake-chroot-ng` експериментальний; перевіряти PTY, `apt`, DNS, TLS, symlink і Android SELinux на цільових девайсах.
- OCI layers потребують коректних whiteouts та безпечного застосування; один `tar` extract недостатній.
- Розмір rootfs/пакетів і час першої інсталяції залежать від образу та мережі; показувати реальні значення, не вигадані оцінки.
- Потрібно окремо перевірити, що `@opencode/cli` має native ARM64 Linux пакет і postinstall працює в Debian та Ubuntu.
- OpenCode `serve`/`web` CLI й механізм UI можуть змінюватися між версіями; закріплювати версію й перевіряти health/UI шлях.
- `chroot-ng` — не sandbox: Shell дає користувачу можливість змінювати власне середовище та файли застосунку. Не запускати неперевірені віддалені скрипти автоматично.
- Складна PTY/multi-tab реалізація потребує окремого процесного сервісу, lifecycle й тестування батареї/пам’яті.

## 15. Межі першого релізу

Перший перевірюваний реліз має включати: Debian Trixie arm64 як стабільно протестований варіант, спільний installer pipeline, OpenCode через офіційний npm пакет, ручну авторизацію, локальний Web/Shell потік і безпечне збереження HOME/workspace. Ubuntu можна показати як доступну опцію лише після перевірки rootfs і повного проходження критеріїв. Advanced multi-tab shell і монетизація — наступні етапи; не імітувати їх тимчасовими кнопками.
